# ADR 0024 — 로컬 Wi-Fi(LAN) 설정 포털 허용

- 상태: **채택(사용자가 권장안 전체 구현을 요청)**. 호스트 테스트 111개와 펌웨어 빌드까지 검증. **기기에서는 아직 실행하지 않았다(BLOCKED_HW).** 날짜 2026-11-12.
- 설계: [2026-11-12 LAN 설정 포털 설계](../superpowers/specs/2026-11-12-lan-settings-portal-design.md)

## 질문
docs/04는 "AP에서만 HTTP 설정 페이지 허용, 기본 AP는 비공개, 최초 등록/롱프레스에서만 10분"으로 정했다. 휴대폰으로 집 Wi-Fi 안에서 기기 IP로 들어가 설정을 바꾸려면 STA(LAN) 주소에서도 설정 페이지를 열어야 한다. 이 규칙을 바꿀 것인가.

## 선택 (제안)
- STA 주소에서도 설정 페이지를 연다. 단 기본값은 **녹색 2초로 10분만 여는 `Button` 모드**이고, 상시 열기(`Always`, USB 전원만)는 사용자가 고르는 선택 항목이다.
- LAN 접근 제어: 기기 e-paper에만 보이는 1회용 페어링 코드 → 세션 쿠키 1개(HttpOnly, SameSite=Strict), CSRF, Host·Origin 허용목록(DNS 리바인딩 방어). 외부 WAN 노출은 계속 금지(포트포워딩·UPnP 안 함).
- 전송은 **평문 HTTP**. 비밀값은 쓰기 전용, 응답·로그·화면에 다시 나오지 않는다.
- SoftAP 포털은 첫 설정·복구·민감한 키 입력 경로로 그대로 둔다.
- 따라오는 변경: 설정 스키마 v3, `refresh_scale_pct`를 빌드 설정에서 저장 설정으로 옮김(ADR 0017 변경), 릴리스 빌드에서 `dev_credentials.h` 경로 제외.

## 다른 선택지
1. 현행 유지(AP 전용): 가장 안전하지만 설정할 때마다 휴대폰 Wi-Fi를 기기 AP로 바꿔야 하고, 그동안 대시보드가 멈춘다.
2. 기기 내 HTTPS(자체서명): 매번 인증서 경고, 사용자가 경고를 넘기는 습관, TLS 서버 RAM 비용. 신뢰 체인이 없어 중간자 방어도 불완전하다.
3. ESP-IDF Unified Provisioning(security2) / Improv BLE: 암호화는 강하지만 전용 앱이나 Web Bluetooth가 필요하고 Wi-Fi 외 설정(키·지역·관심종목)을 담는 UI가 없다. BLE 스택 RAM 비용도 크다.
4. HTTP Basic/Digest 인증: Basic은 매 요청 평문 비밀번호, Digest는 기기별 호환 문제 보고가 있다.

## 근거
- 사용성: 휴대폰 망 전환 없이 설정, 대시보드 계속 동작(USB).
- 공격 면 축소: 기본은 필요할 때만 10분, 인증은 물리적 근접(화면 코드)으로.
- 기존 보안 핸들러(CSRF·상한·비반사·2단계 초기화, 호스트 테스트 30개)를 그대로 재사용.

## 위험 (수용 여부를 사용자가 결정)
- 같은 Wi-Fi 비밀번호를 아는 사람이 무선을 캡처하면 LAN 포털에서 입력하는 키를 볼 수 있다. 완화: 경고 문구, AP 경로 유지, 세션 짧게. 완전한 방어는 아니다.
- `Always` 모드에서는 LAN의 다른 기기가 로그인 화면에 닿을 수 있다(코드 없이는 진행 불가, 시도 제한).
- `.local` 이름은 OS·VPN에 따라 안 될 수 있다. IP를 기본 안내로 한다.

## 검증 증거
- 호스트 테스트 111개 통과(신규 14개: 설정 v3·순환·요청 검사·페어링·LAN 핸들러·관심종목 편집기·기기 탭·Wi-Fi 검색·백업). 펌웨어 빌드 성공(두 환경). 변이 확인 2건(Host 검사 제거, 세션 검사 제거)에서 테스트가 실패함. 실기 항목은 설계 문서 §11, 전부 미실행.

## 되돌리는 방법
- 설정 `lan_mode=Off`로 현행과 같은 AP 전용 동작. 코드 수준 회귀는 `LanPortal_esp32` 배선 제거만으로 가능하도록 모듈을 분리한다.

## 구현 현황과 설계에서 달라진 점 (2026-11-12)

권장안으로 구현: 기본 모드 `Button`, 관리자 비밀번호 없음, 로그인 시 화면 자동 전환 없음, 평문 HTTP 허용 + 경고 문구, 저장 후 재부팅.

- 구현: 스키마 v3(+ v2 읽기), 빌드 시 자격정보 분리(`reterminal_e1001_dev`), `PortalAuth`/`RequestGuard`/`PortalHandler`(LanPaired), `LanPortal`(논블로킹), `PortalRunner`(LAN 우선, AP 폴백, 배터리는 10분 블로킹), 기기 탭 주소·코드 표시, `main.cpp` 연결.
- **페어링 코드 방식 변경**: 설계는 "로그인 요청 때 발급, 1분 1회 화면 갱신"이었으나, 구현은 포털을 열 때 발급하고 1회 사용 또는 10분 경과/5회 실패 잠금 뒤에 새로 발급한다. 표시가 바뀔 때만 기기 탭을 다시 그린다. 원격 요청이 화면 갱신 빈도를 마음대로 올리지 못하게 하는 효과는 같다.
- 포털은 한 번에 요청 하나만 처리한다(`BoundedServer`의 accept 방식 유지).
- **주변 Wi-Fi 검색(구현)**: Wi-Fi 화면의 "주변 Wi-Fi 검색" → 어댑터가 블로킹 검색(약 2~5초) 후 최대 15개(신호 순, 중복·숨김 제외)를 목록으로 제공. 이름은 번호로만 고르고(서버가 가진 값만 저장), 직접 입력이 우선. 검색 중 휴대폰 응답은 이미 나간 뒤라 끊기지 않는다.
- **설정 백업·복원(구현)**: `/backup`. 내보내기와 가져오기 모두 지역·관심종목·공급자 사용 여부·기기 설정만 다루고, Wi-Fi와 API 키는 넣지도 받지도 않는다. 가져오기는 항목마다 검증하고 하나라도 틀리면 아무 것도 적용하지 않으며, 오류에는 필드 이름만 나온다. 1536바이트 제한. 저장은 접속 시험 없이 재부팅.
- 추가: 관심종목 행 편집기(종목 코드·시장 선택, 종목명 표시, 중복·형식 검사), 자동 순환 설정([ADR 0025](0025-page-auto-rotation-and-market-fsc-close.md)).
- **빌드 환경 변경(중요)**: 기본 환경 `reterminal_e1001`은 더 이상 `include/dev_credentials.h`를 컴파일하지 않는다. NVS가 비어 있는 기기에 올리면 SoftAP 설정 포털(KDASH-E1001-XXXX)이 뜬다. 지금까지처럼 로컬 자격정보를 내장하려면 `pio run -e reterminal_e1001_dev`를 쓴다.

## 실기 검증 (2026-11-12, E1001 COM5, 개발 환경 빌드)

검증용으로 `-D KDASH_DEV_LAN_ALWAYS=1 -D KDASH_DEV_ROTATE_MIN=1`(환경변수로만 지정, 저장소 설정 아님)을 켠 빌드를 올려 확인한 뒤, 기본 설정 빌드로 다시 올렸다. 업로드는 해시 검증을 통과했다.

| 항목 | 결과 |
|---|---|
| 포털 열림 | `portal: lan open (always)`, PC(같은 LAN)에서 `http://<기기 IP>/` 응답 확인 |
| 로그인 전 보호 | `/keys /wifi /export /backup /device /status` 모두 401. 로그인 화면에 코드 없음 |
| Host 검사 | 위조 Host(`evil.example`) 421, 정상 Host 및 `IP:80` 200 |
| Origin 검사 | Origin 없음/외부 Origin의 POST 403. 세션 없는 `/save` 401 |
| 요청 형식 | 쿼리 문자열은 연결 종료(거부), PUT 405. 이후에도 정상 응답 |
| 잠금 | 틀린 코드 5회 → `[200,200,200,200,429]`, 이후 429 |
| 보안 헤더 | `no-store`, `nosniff`, `no-referrer`, CSP 확인 |
| 자동 순환 | 로그 `rotate: page 0 -> 1`, `1 -> 0` 반복(검증용 1분 간격, 장 시간 안) |
| 금융위원회 | 같은 부팅에서 `provider=5 OK`(요청 4건) |
| 기본 설정 빌드 | 부팅 정상. Button 모드라 80번 포트가 닫혀 있음(연결 거부) |

**미검증(실기)**: 페어링 코드는 화면에만 표시되어 로그인 이후의 흐름(구역 저장, Wi-Fi 검색, 백업 가져오기, Wi-Fi 변경 성공/실패 복귀), `.local` 이름 해석, 배터리 전원의 10분 블로킹 포털, 화면에 코드가 실제로 보이는 모습, 시장 화면의 종가 표기는 확인하지 못했다. 이 항목은 사람이 기기 앞에서 확인해야 한다.

관찰: 짧은 시간에 재부팅을 반복하자 KIS가 일시적으로 `RATE_LIMITED`(토큰 발급 제한)였다가 몇 분 뒤 회복했다. 환율은 한 번 `PROVIDER_ERROR`(전송 실패)였고 재시도 대기 중이라 회복 여부는 확인하지 못했다.

## 사후 수정: 실제 브라우저에서 "출처 확인 실패" (2026-11-12)

- 증상: 올바른 페어링 코드를 입력해도 로그인 POST가 403 "출처 확인 실패".
- 원인: 응답 헤더 `Referrer-Policy: no-referrer`. 이 정책이면 브라우저는 같은 사이트 폼 POST에도 `Origin: null`을 보낸다(Fetch 사양). Origin 검사가 `null`을 거부했다.
- 놓친 이유: 위 실기 검증은 `Origin: http://<기기 IP>`를 직접 넣은 요청이었다. 실제 브라우저의 Origin/Referer 동작은 검증하지 않았다. 호스트 테스트도 같은 가정이었다.
- 수정: `Referrer-Policy: same-origin`(같은 사이트 POST는 실제 Origin 전송), 그리고 `Origin: null`은 Origin이 없는 것으로 보고 Referer로 확인(Referer도 허용 호스트일 때만 통과, 외부·없음은 거부). 회귀 테스트 추가.
- 남은 확인: 수정 후 실제 브라우저(Android Chrome 등)에서의 로그인 성공은 사용자 확인이 필요하다.

## 보완 (2026-11-12, 사용자 보고 2건 + 점검)

| 항목 | 원인 / 변경 | 검증 |
|---|---|---|
| Wi-Fi 검색이 안 보임 | 검색은 응답을 보낸 뒤 실행되는데, 안내 화면에 Wi-Fi 화면으로 가는 길이 없었다. 그 화면을 새로고침하면 검색만 다시 보냈다. → 6초 뒤 `/wifi`로 자동 이동(meta refresh)하고 링크 제공. Wi-Fi 화면에 검색 중/실패/결과 없음 표시. 어댑터는 실패(음수) 시 1회 재시도, 개수만 로그(`portal: wifi scan found=N`). | 실기: 연결 상태 검색 API `found=16`(검증 빌드 자체 점검). 호스트 테스트. 로그인 후 실제 화면 흐름은 사용자 확인 필요 |
| 종목명이 고정됨 | 이름을 저장된 값으로 서버에서 한 번만 그렸다. → 같은 출처 스크립트 `/app.js`(공개 종목명 표 76개)가 입력할 때마다 이름을 바꾸고, 이름으로 고르는 목록(datalist)을 채운다. CSP에 `script-src 'self'`만 추가(인라인 스크립트 금지 유지). 스크립트가 없어도 저장 화면에 종목명 요약을 보여 준다. | 실기에서 받은 `app.js`를 Node 가짜 DOM으로 실행해 이름 변경·안내·목록·비밀번호 보이기 확인. 실기 CSP/Host 검사 확인 |
| 10분 창 | 처음 연 시각 기준이라 편집 중에도 닫혔다. → 로그인된 요청이 올 때마다 연장(마지막 활동 기준 10분). | 호스트 테스트 |
| 위치 입력 | 위도·경도를 넣으면 기상청 격자로 계산(`LatLonToGrid`, 둘 다 있어야 함, 한국 범위 밖 거부). | 호스트 테스트(서울 60,127 / 부산 98,76) |
| 메뉴·상태 | 메뉴에 현재 설정 요약(Wi-Fi 이름, 지역·격자, 관심종목 이름, 키 등록 여부, 순환). 상태 화면에 공급자별 수신 상태(기기 탭과 같은 문구, 5초 캐시). | 호스트 테스트 |
| 기타 | 비밀번호 칸 "보이기"(스크립트), 저장·재시작·가져오기 뒤 25초 뒤 자동으로 메뉴 이동 안내. | 호스트 테스트 |
