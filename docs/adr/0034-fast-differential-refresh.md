# ADR 0034 — 빠른 차분 갱신(흑백) + 5회마다 4계조 전체 갱신

- 상태: 채택(설정 기본 꺼짐). 호스트 테스트, 타깃 빌드, 실기 UART 동작(빠른 갱신 2회 성공)까지 확인했다. 화면 극성·잔상·글꼴 육안 확인과 5회 주기 전체는 **BLOCKED_HW**다. 날짜 2026-11-24 KST.
- 요청: 화면 전환 때 전체 갱신 때문에 패널 전체가 깜빡인다. 부분 갱신을 N회 한 뒤 전체 갱신하는 방식으로 깜빡임을 줄인다.
- 이전 결정: [ADR 0018](0018-flicker-reduction-and-partial-refresh.md)은 부분 갱신을 검토만 하고 켜지 않았다. 근거 가운데 "GDEY075T7 드라이버 원문 404"는 이번에 해소했다.

## 새 근거 (확인일 2026-11-24)

공식 E1001 예제 `GxEPD2_reTerminal_E1001.ino`가 쓰는 드라이버의 원문을 읽었다. GxEPD2 master `src/gdey/GxEPD2_750_GDEY075T7.{h,cpp}`이다. 커밋 해시와 버전은 기록하지 못했다.

| 항목 | 원문 값 | 이 ADR에서 쓰는 방식 |
|---|---|---|
| `hasFastPartialUpdate`, `useFastPartialUpdateFromOTP` | true | OTP에 내장된 빠른 부분 파형을 쓴다. 레지스터 LUT는 올리지 않는다 |
| `_InitDisplay` | 0x00=1F, 0x01=07 07 3F 3F 09, 0x06=17 17 28 17, 0x61=800×480, 0x15=00, 0x50=29 07, 0x60=22, 0xE3=22 | 같은 값을 쓴다 |
| `_Init_Part` (OTP fast) | 0xE0=02, 0xE5=6E, 이어서 0x04(전원 켬) | 같은 값을 쓴다 |
| 버퍼 | 0x10=이전 프레임, 0x13=새 프레임, CDI 0x29(N2OCP, DDX=01 → 데이터 1이 흰색) | 같은 극성이다. 두 평면을 매번 호스트 사본에서 다시 쓴다 |
| `partial_refresh_time` / `full_refresh_time` | 450 ms / 1200 ms (원문 측정값) | 이 기기에서는 아직 측정하지 않았다 |
| N회 권장 | 원문에 없음 | 5회는 [ADR 0032](0032-device-document-audit.md)의 Good Display 권장값이다 |

GxEPD2는 GPL-3.0이다. 코드는 복사하거나 링크하지 않았다. 하드웨어 레지스터 값만 참고했고, 시퀀스는 `Uc8179.cpp`에 직접 구현했다([ADR 0004](0004-epaper-driver.md)와 같은 방침).

## 선택

1. `epd::PushFastFrame(old, old_any_ink, new)`: 리셋 → 위 초기화 → 0x10/0x13에 흑백 평면 전송 → 0x12 → 전원 끄기와 deep sleep. 전체 창 차분 갱신이다. 영역(window) 부분 갱신은 이번 범위에 넣지 않았다.
   - 2bpp Canvas를 임계값으로 자른다. 잉크 `>= 2`(진한 회색, 검정)는 검정이고 나머지는 흰색이다.
   - 직전 프레임이 4계조 전체 갱신이었으면(`old_any_ink`) 이전 평면에서 잉크가 조금이라도 있는 픽셀을 검정으로 본다. 그래야 옅은 안티앨리어싱 픽셀이 흰색으로 구동되어 남지 않는다.
2. `ui::FastRefreshCaps(설정, OTP 파형, 직전 프레임 보유)`: 세 조건이 모두 참일 때만 부분 갱신을 쓴다. 판단은 기존 `DecideRefresh`/`NoteRefreshDone`을 그대로 쓴다. 결과는 Full → 빠른 갱신 5회 → Full(4계조, 잔상 제거) 순서로 반복된다.
3. `FramePresenter`: 직전 프레임 사본 96 KB를 **PSRAM에만** 둔다. PSRAM이 없으면 기능을 끈다. 빠른 갱신이 실패하면 같은 사이클 안에서 전체 갱신으로 대체하고, 다음 프레임은 Full로 강제한다. 설정 포털 화면을 띄운 뒤에도 다음 페이지는 Full이다. 로그에 `mode=fast|full partials=N`을 남긴다.
4. 설정 `DeviceConfig::fast_refresh`(기본 꺼짐)를 추가하고 스키마를 v5로 올렸다(마지막 1바이트 추가).
   - v2~v4 저장값은 이 값을 꺼진 상태로 이전한다. 0과 1 외의 값은 거부한다.
   - DATA 지문은 끝의 기기 전용 2바이트를 빼고 계산한다. 따라서 캐시 정체성은 v3/v4와 같다.
   - 포털 기기 화면에 체크박스를 추가했고, 백업 JSON 키 `fast_refresh`도 추가했다.

## 동작 범위

- **USB 전원(깨어 있음)**: 버튼으로 화면을 넘기거나 자동 순환하거나 데이터가 바뀔 때 빠른 갱신을 쓴다. 6번째마다 4계조 전체 갱신을 한다.
- **배터리 deep sleep**: 깨어날 때마다 PSRAM이 비어 있으므로 항상 전체 갱신이다. 지금 동작과 같다.
- 시계만 바뀐 경우 30분 동안 건너뛰는 규칙(ADR 0018)은 그대로다. 빠른 갱신으로 시계를 자주 갱신하면 전체 갱신 횟수가 늘어나므로 바꾸지 않았다.

## 대안과 기각 이유

- **모두 흑백으로 그리고 빠른 전체 갱신(약 1.2초, 0xE5=5A)만 쓰기**: 깜빡임 시간만 줄고 깜빡임 자체는 남는다. 4계조 글꼴도 잃는다.
- **모두 흑백으로 그리기(전체 갱신 포함)**: 차분 갱신의 이전 상태가 정확해지지만, 전체 갱신 화면의 4계조 품질까지 잃는다. 사용자 권장안(4계조 Full 유지)과 다르다.
- **배터리 모드에서 이전 프레임 복원**(캐시 스냅샷으로 다시 그린 뒤 RTC CRC 대조): 시계 영역 때문에 CRC가 일치하지 않는다. 플래시에 저장하는 방안은 마모가 생긴다. 후속 과제로 남긴다.

## 위험 (실기에서 확인할 것)

- 원문 주석은 `useFastPartialUpdateFromOTP`가 "초기 배치 패널에서는 false"라고 한다. 이 기기는 `waveform=internal-otp`로 판별됐지만 OTP에 빠른 부분 파형이 실제로 있는지는 모른다. 증상은 화면이 바뀌지 않거나, 깨지거나, 반전되는 것이다. 대응은 설정을 끄는 것이다.
- 극성: GxEPD2 관례(CDI 0x29, 1=흰색)를 따랐다. 4계조 경로는 이 기기에서 공식 관례와 극성이 반대였다(ADR 0012). 빠른 갱신 화면이 반전되면 0x50 값이나 비트 극성을 바꿔야 한다.
- 온도를 0x6E로 고정 주입한다. 원문은 저온에서는 빠른 모드를 끄라고 한다. 저온 화질은 미검증이다.
- 빠른 갱신 화면에는 글자 가장자리 회색이 없다. 4계조 Full 화면과 다음 빠른 화면 사이에 글꼴 질감 차이가 보인다.
- 잔상: 5회 누적 뒤의 잔상 정도와 100회 반복(U-03, U-15)은 측정하지 않았다.

## 실기 결과 (2026-11-24, USB)

- 새 개발 환경 `reterminal_e1001_fast_dev`(`KDASH_DEV_FAST_REFRESH`)를 추가했다. `config: source=dev`(저장 설정 없음)일 때만 기능을 켠다. 이 기기는 원래 이 상태로 동작하므로 포털 없이 검증할 수 있다. 저장된 설정이 있으면 포털 값이 우선한다. 릴리스는 기본 환경만 쓴다.
- UART: `mode=full` 4.74초 → `mode=fast partials=1` 1.99초 → `partials=2` 1.99초, 모두 `ok=1`. 원문의 450ms보다 4배 이상 길다. SPI 2MHz로 평면 2개(96KB)를 매번 보내는 시간이 약 0.86초이고 파형 구동이 약 0.92초다. 전환당 4.7초 깜빡임에서 2.0초 안팎의 차분 갱신으로 줄었다.
- 전송 시간 개선 후보(미적용): 0x10 평면은 직전 프레임과 같아서 다시 보내지 않아도 되는지(패널 RAM이 deep sleep 때문에 지워지므로 지금은 필요), SPI 클럭 상향. 둘 다 실기 검증이 필요해 이번에는 건드리지 않았다.
- 10분 수집 동안 빠른 프레임이 2번뿐이라 5회 뒤 전체 갱신으로 돌아오는 주기는 관찰하지 못했다. 단위 테스트(`test_fast_refresh_caps_and_cycle`)로만 확인했다.

- 호스트: `test_fast_frame_register_sequence_and_planes`, `test_fast_frame_rejects_bad_input_and_timeout`, `test_fast_refresh_caps_and_cycle`(F,P×5,F 순서와 배터리/설정 꺼짐), `test_settings_v5_fast_refresh_roundtrip_and_migration`, `test_fast_refresh_backup_roundtrip`, 포털 저장 확인. C++ 160개, Python 209개 통과.
