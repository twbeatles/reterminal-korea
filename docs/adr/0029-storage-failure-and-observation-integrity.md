# ADR 0029 — 저장 장애 재시도와 장기 관측 신뢰성

- 상태: 구현 및 Host/Build 검증, 실기 적용 대기, 2026-11-13. 기준 main `26bfd6f`.
- 질문: Flash 저장 실패와 진단 누락이 장기간 반복되어도 쓰기 폭주와 잘못된 정상 판정을 막는가?
- 관찰: RuntimeStore는 성공한 쓰기만 예산에 반영하여 실패 때 30초마다 다시 쓸 수 있다. PMIC는 정책 판정 뒤 별도 진단 읽기를 수행해 그 실패가 반환 상태에 반영되지 않는다. soak 도구는 health가 이어지면 저장/패널/충전 오류나 UART 수집 손실을 놓칠 수 있다.
- 선택(LT-11): 저장 I/O를 시도하기 전에 하루 48회 예산을 예약한다. read-back 실패·메모리/검증 실패 후 5분 대기한다. 시계 역행 시 대기 기준을 한 번 재설정하며 역행으로 일일 예산을 초기화하지 않는다. 기존 저장 포맷을 유지한다. 완전히 실패한 쓰기 예산의 RAM 기록은 전원 상실까지 영속적이라고 주장하지 않는다.
- 선택(LT-12): 충전 정책의 동일 읽기/쓰기 트랜잭션에서 확인된 cfg/timer/status만 진단에 사용한다. 상태 읽기도 실패하면 Fault, 미지원/오류의 미확인 값을 확인 성공으로 표시하지 않는다.
- 선택(LT-13): strict USB 관측은 checkpoint/패널/충전/watchdog 등록 오류도 검출한다. capture sidecar의 끊김·데이터 폐기·중단을 검사하는 옵션을 추가한다. 확인한 범위를 JSON에 명시한다. 기존 health만 분석한 결과를 전체 수집 무결성 확인으로 격상하지 않는다.
- 운영 경계: 현재 24h 수집 PID와 기기를 재시작하지 않는다. 추가 펌웨어는 Host/Build 검증 후 대기하며 기존 이미지의 시험과 구분한다. 실행 중 캡처는 시작 당시 Python 코드로 동작하므로 새 logger 기능이 소급 적용됐다고 주장하지 않는다. 완료 시 sidecar 포함 재분석이 필요하다.
- 대안: 무조건 주기 재부팅(장애 근거와 연속 시험을 잃음), 저장 실패 즉시 재시도(Flash/CPU 부담), 모든 HTTP 실패를 soak FAIL로 취급(복구 가능한 외부 장애와 기기 장애 혼동).
- 검증: 저장 실패/예산/시계 역행·회복, PMIC 상태 읽기 실패/비트 보존, strict 로그/sidecar 누락 회귀. 결과는 `evidence/long-term-followup-2026-11-13/summary.md`.
- 되돌리기: 스키마 변경 없음. 기존 firmware로 복귀 가능. 분석기는 기존 단일 로그 호출도 지원한다.
